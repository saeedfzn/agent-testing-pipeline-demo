How I build and test agents before they ship

Faizaan Saeed · built for an AI Engineer (agentic AI start-up) application

An agent that works in a demo is easy. One you can put in front of customers needs four things around it: a clear setup, a review that hunts for what's wrong, tests that catch regressions, and a pipeline that refuses to ship a worse version. This page walks through all four, then shows what I'd watch once it's live.

What this is: a simulated walkthrough with made-up data. The support-triage agent, its eval results, the pipeline runs and the monitoring figures are invented to show the method; nothing here calls a model. The section on how I work with Claude Code is real: daily use with MCP servers, skills and sub-agents, review panels of up to 69 sub-agents, and a client system delivered through 56 versioned releases.

2 · Adversarial review panel

Before a change merges, a panel of reviewer sub-agents each attacks it from one angle. Reviewers are deliberately suspicious, so some findings are wrong. Nothing is acted on until a person checks the evidence. Here the panel reviews a pull request that made the agent's replies friendlier. Read each finding and its evidence, then mark it verified (a real issue) or rejected (a false positive).

3 · Eval suite with regression tracking

Twelve fixed test tickets with the expected category, priority and action. The agent returns structured output, so grading is a deterministic comparison of fields, not a model marking its own homework. The grading is deterministic; the model isn't, so a real suite runs each case more than once and counts a flaky case as a fail. A release needs a pass rate of at least and no case that passed in the baseline (the last version to clear the gate) may fail now.

4 · The CI/CD pipeline

The evals run on every pull request and every push to main. Deployment jobs only run after the eval gate passes, and production needs a manual approval. Run a normal release, then simulate the regressed version from section 3 and watch the pipeline refuse to deploy it.

.github/workflows/agent-ci.yml

name: agent-ci

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: agent-ci-${{ github.ref }}
  # cancel superseded PR runs, but never a deploy on main part-way through
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements-dev.txt
      - run: ruff check .

  unit-tests:
    needs: lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements-dev.txt
      - run: pytest tests/unit -q

  agent-evals:
    needs: unit-tests
    runs-on: ubuntu-latest
    env:
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements.txt
      - name: Run eval suite
        run: python -m evals.run --suite evals/triage.jsonl --out eval-report.json
      - name: Gate on pass rate and regressions
        run: >
          python -m evals.gate --report eval-report.json
          --baseline evals/baseline.json
          --min-pass-rate 0.90 --fail-on-regression
      - uses: actions/upload-artifact@v7
        if: always()
        with:
          name: eval-report
          path: eval-report.json

  deploy-staging:
    needs: agent-evals
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v7
      - run: ./scripts/deploy.sh staging
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

  smoke-test:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: python -m smoke --base-url "${{ vars.STAGING_URL }}"

  promote:
    needs: smoke-test
    runs-on: ubuntu-latest
    environment: production   # required reviewer set in repo settings
    steps:
      - uses: actions/checkout@v7
      - run: ./scripts/deploy.sh production
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

A sketch written for this demo, not lifted from a client project. The eval and smoke-test modules are placeholders for the project's own scripts. The same shape maps onto Azure Pipelines stages, with environment approvals in place of the production reviewer.

How I work with Claude Code

This part isn't simulated. It's how I build day to day.

Project instructions

A CLAUDE.md that carries the project

  • Each project has a CLAUDE.md: what the spec of record is, the non-negotiable rules from the signed scope, and the traps found so far.
  • When something costs me time, I write it down there the same day, so a fresh session doesn't repeat it.
Tools & skills

MCP servers, tool calling, reusable skills

  • I connect Claude Code to real systems through MCP servers and tool calls, and package repeated workflows as skills instead of re-explaining them.
  • When an MCP integration kept failing, I noticed the two tools that worked took no parameters and the two that failed took a directory. Probing the JSON-RPC showed the server expected a different parameter name from the one its schema advertised.
Sub-agents

Review panels, like section 2

  • I use sub-agents for parallel work and for adversarial review.
  • In one review I ran up to 69 reviewer sub-agents. They overturned 28 of 62 claims, and I checked every finding by hand before acting on it.
Verification habits

Prove it, don't assume it

  • Nothing is "done" until it has been tested. I keep what I've verified separate from what I've only inferred.
  • I check the system of record, not the UI's word for it: a release is confirmed on the version history, not on a "saved" message.
